## 2) ما تحققتُ منه (في صندوقي، مستوى L1)

- **57 اختباراً ناجحاً** (Python 3.12.3، مكتبة قياسية فقط).
- **الحارس على شجرة مُعاد بناؤها** من ملفات المشروع وملفاتي (مع بدائل لاختبارات V2-01 غير الموجودة عندي): `errors=0 warnings=0 allowed=0` على 53 ملفاً، exit 0. ضابط سلبي: أضفتُ `print` و`random` عند الاستيراد فرفضهما الحارس.
- **اختبار التخريب:** 8 تعديلات مقصودة في `normalizer.py` (أول رسالة فقط، أول entry فقط، مفتاح حالة بلا الحالة، هاتف إلزامي، هوية رسالة النظام، هاتف النظام الجديد، بلا إزالة تكرار، بلا حد للتسليم) يمسكها الاختبار كلها، وتعديل بلا أثر لا يُعدّ تخريباً.
- **«لا يرمي أبداً»:** تبديل كل موضع في 7 حمولات حقيقية بـ15 قيمة شاذة، و3000 شجرة عشوائية. وأثبتُّ أن الاختبار يمسك خللاً حقيقياً حُقن عمداً.
- **الأمثلة وجدت خللاً حقيقياً أثناء البناء:** رسالة `user_changed_user_id` لا تحمل `from` وهويتها داخل `system.user_id`، فكان المُطبِّع يسقطها. أُصلح وله سيناريو N11.

## 3) قيود Cloudflare Workers التي بُني عليها (من وثائقها، جُلبت 2026-11-23)

- **10ms CPU لكل طلب في الخطة المجانية** (انتظار الشبكة لا يُحسب) و**50 طلباً فرعياً**: لذلك المُطبِّع نقي، بلا regex، بلا نسخ عميقة، ومسار الاستلام في 02B سيستعمل طلباً فرعياً واحداً. *CPU الفعلي على Worker غير مقيس* (V2-11).
- **اللقطة (snapshot):** يُنفَّذ الاستيراد العلوي لحظة النشر ويُصوَّر الذاكرة، أما الاستيراد داخل المعالج فيُنفَّذ وقت الطلب ويُحسب من وقته. لذلك محدِّد 02B سيُستورد في رأس `webhook.py` (بحماية `ImportError`) لا داخل الدالة.
- **الساعة لا تتقدم أثناء الحساب البحت** وتتقدم بعد I/O: `stages_ms` للمراحل بلا I/O ستُقرأ صفراً في الإنتاج وهذا ليس خللاً.
- **حد متغير البيئة 5KB**، وبدء التشغيل ≤ 1 ثانية: لا مشكلة لـ`V2_FLAGS` و`V2_ALLOWLIST`.
- **Meta تعيد المحاولة أياماً عند غير 200:** من هنا حماية «الحبّة السامّة» (ADR-10 البند 6).
- المصادر: صفحة Workers limits، وصفحة how-python-workers-work، وصفحة runtime-apis/performance في developers.cloudflare.com.

## 5) ما لم أتحقق منه (صراحةً)

1. تشغيل المُطبِّع على Worker حقيقي: زمن وCPU (V2-11). ظهور سطور السجل في Workers Logs (02B).
2. الحمولات السبع `simulator-only` ضد مرجع Meta الحي (تُراجع في V2-10 أو بحمولات حقيقية).
3. صفحة BSUID تحمل تحذير «September 15, 2026 update» ولم أقرأ نص إدخاله في سجل التغييرات (لم يُجلب ذيل الصفحة). **يُقرأ في بداية 02B قبل أي تفعيل.**
4. أنواع `edit` و`revoke` تظهر في فهرس مرجع رسائل Meta ولم أرَ شكلها: تُقرأ الآن `unsupported` مع `orig_type`. على V2-04 ألا يردّ عليها.
5. موضع `origin` في بطاقة `contacts` (على الرسالة أو داخل البطاقة): يُدعم الموضعان.
6. لم يُشغَّل شيء من V1: **لم يُمَسّ أي ملف V1 في 02A**، فلا «سجل تعديل ملف مجمّد» لهذا الجزء.

## 7) مواصفات V2-02B (الجزء الثاني): ما يلزم تنفيذه

1. **قراءة أولاً:** إدخال «September 15, 2026» في سجل تغييرات Meta (البند 5.3).
2. **SQL:** `sql/migrations/002_inbox_functions.sql` وترحيلها العكسي، قابلة للتكرار، `security invoker`، `set search_path = public`، `revoke ... from public, anon, authenticated` ثم `grant execute ... to service_role`، وتنتهي بـ`notify pgrst, 'reload schema'`:
   - `inbox_accept(p_phone_number_id text, p_events jsonb) returns jsonb`: يبحث عن المتجر بالأعمدة المطلوبة فقط (لا `select *`)، ويُدخل كل حدث `on conflict (store_id, wamid) do nothing`، ويرجع `{store_found, store_id, routed, results:[{wamid, inserted, id}]}`. عنصر الحدث: `{wamid, kind, from_phone, from_bsuid, status: pending|done, event}`، و`finished_at = now()` عند `done`. إن كان `stores.features -> 'v2_pipeline' = false` فيرجع `routed=false` بلا إدخال (مفتاح الإيقاف لكل متجر، ADR-2).
   - `inbox_claim(p_id uuid, p_lock_seconds int default 60) returns boolean`: من pending أو من processing منتهي القفل إلى processing، مع `attempts + 1`.
   - `inbox_finish(p_id uuid, p_status text, p_error_code text default null) returns boolean`: من processing فقط، وحالة النهاية done أو failed أو ignored.
   - `inbox_claim_stale(p_kind text default 'message', p_limit int default 10, p_pending_older_than_seconds int default 45, p_lock_seconds int default 60, p_max_attempts int default 3) returns setof inbound_events`: `for update skip locked`، وما بلغ `p_max_attempts` يصير failed برمز `INTERNAL_DEADLINE`. قفل 60 ثانية لأن `ctx.waitUntil` يعيش نحو 30 ثانية بعد الردّ.
2. **Python:** `ports/db.py` (`rpc(name, params)`) و`ports/clock.py`؛ `adapters/supabase_rest.py` (طلب `POST {url}/rest/v1/rpc/{name}` بـ`httpx.AsyncClient` جديد لكل نداء، مهلة 5 ثوان، ويُصنَّف الخطأ: فئة SQLSTATE 22 أو 23 هي `DB_CONSTRAINT`، وغيرها `DB_UNAVAILABLE` أو `DB_UNEXPECTED`)؛ `adapters/system_clock.py`؛ `adapters/worker_env.py` (يبني `FlagSettings` من `V2_FLAGS` و`V2_ALLOWLIST` ويخزّنه مؤقتاً بمفتاح النصين)؛ `inbound/inbox.py` (سياسة الحفظ من ADR-10 فوق المنفذ)؛ `pipeline/entry.py` (`route_delivery(payload, env, ctx)` يرجع `None` لـV1 أو `Verdict(status, body)`) و`pipeline/build.py` (الوحيد الذي يستورد المحوّلات).
3. **قواعد المحدِّد:** `v2_pipeline` مطفأ أو المتجر خارج القائمة أو أكثر من `phone_number_id` في التسليم: `None` (V1 كما هو). متجر مجهول: 200 + `INBOUND_STORE_UNKNOWN`. فشل الحفظ: 503 إلا `DB_CONSTRAINT` فـ200. خطأ في المُطبِّع قبل أي حفظ: `None` (V1).
4. **تعديل V1 (الوحيد):** استيراد علوي محمي في رأس `webhook.py`، وكتلة داخل `receive_message` بعد `payload = await request.json()` **وقبل** سطر `logger.info("received webhook payload...")` تستدعي `route_delivery` داخل `try/except` يسجّل ويكمل بـV1. يحتاج المثبّت قدرة «استبدال ملف موجود بشرط أن تطابق بصمته القديمة المتوقعة» (قالب المثبّت الحالي يرفض كل ملف موجود يختلف). يُسجَّل في محضر 02B «سجل تعديل ملف مجمّد» ولا يُغلق إلا بنجاح اختبارات V1 كلها والأعلام مطفأة.
5. **الاختبارات:** L1 (منفذ وهمي + تخريب ≥ 5 للصندوق وللمحدِّد)؛ L2 (تمرير `receive_message` عبر FastAPI بأعلام مطفأة ثم مشغَّلة)؛ L3 على مشروع TEST بالنمط نفسه لـ`test_schema_contract_real.py`. وL3 الخاص بالترحيل 001 لم يُشغَّل بعد حسب V2-01.md، وهو شرط مسبق لـL3 الجديد.
6. **ممنوع في 02B:** تفعيل `V2_FLAGS` على أي نشر حي. لا ردود من V2 قبل V2-08.
